 250|for `trees.c`, `infblock.c` and `infcodes.c` the padding target collapses to whatever little the
 251|metadata happens to know. `trees.c` reports `+5376 over` while its object is **exactly the span
 252|between its own VAs** (`0x10008800 - 0x10006ec0 = 6464`), i.e. it is not over at all. The script's
 253|own docstring warns about this at the `want` computation ("`want` is only as complete as the
 254|metadata ... and then `want` understates the reference span").
 255|
 256|Split correctly: **25 game files, 816 bytes of genuine overage**, against **3 zlib files, 5,680
 257|bytes of phantom overage**. Read the game lines; ignore the zlib ones.
 258|
 259|**Only SHORT objects can be padded** — `pad_short_functions.py`'s own docstring says a longer one
 260|"cannot be cut without losing code". So for these 28 files the composition has *no slack*: any
 261|edit that grows the object, and on a file already over budget even an edit that keeps its size,
 262|moves the symbols after it.
 263|
 264|That is the mechanism behind three rounds of failures. Round 869's `gm_FindNextFilteredEntity`
 265|change took `spiel_dumpD.c.obj` from 1015 to 1024 bytes and the link reported "COMPOSITION
 266|COLLAPSED: only 0 symbols landed at their reference VA" — because that file was **already 16 bytes
 267|over**, so the composition had nothing left to absorb. The same applies to `LONG` file-mates in
 268|`ErrorModule2.c`, `vfs.c`, `vfs2.c`, `infblock.c` and 23 others.
 269|
 270|**Practical consequence, and the check to run first:** before reshaping any function, look up its
 271|file in the pad report (`grep '<file>.obj' .scratch/gate-link.log`). A `LONG` line means that file
 272|cannot absorb a size change at all and the only adoptable edits are ones that *shrink* it by at
 273|least the stated overage. A file with no line either is within budget or was padded.
 274|
 275|**Applied to the 19 carriers (round 872): 16 are in files WITHIN budget and only 3 are blocked.**
 276|
 277|```
 278|blocked (LONG file)                 within budget
 279|vfs_OpenStream        by  32        gm_AllocSpieler, CrashDump, cm_ExSellObjekt,
 280|spiel_dumpD           by  16        ls_LoadBuildingEntityState, gv_ExAllocGraveyardWorker,
 281|spiel622              by 112        cm_ExCopyEntityData, ServerMainThread, gm_AllocGebaeude,
 282|                                    ahm_ExAllocAlchemist, m_AllocTracked, srv_LoadBuf,
 283|                                    gm_ObjectsAvailble, vfs_ReadCompressed, cm_ExProdObjekt,
 284|                                    cm_ProcessCommandQueue          (15 total)
 285|```
 286|
 287|Rounds 868-870 were spent on `gm_FindNextFilteredEntity`, which is in `spiel_dumpD` — one of the
 288|**three blocked** files. The right move was to work an unblocked carrier, and the check that would
 289|have shown that costs one command. **Run it before choosing a function, not after a failed probe.**

 291|## 6e. `cflags` in the metadata can crash the compiler on a CMake-flag-pinned file (round 877)
 292|
 293|**Correction (round 878): the flags in this entry were misread.** `ls_LoadBuildingEntityState`
 294|(`0x100128f0`) compiles with **`/O2 /Gd /REBREW_TOOLCHAIN:msvc-6.0-sp5-pp`** — the sp5-pp toolchain
 295|pin only, **no `/Oa /Ow`**. Round 877 read a neighbouring file's flag tail. The mechanism this
 296|section describes still holds (a CMake pin the metadata does not carry, and a `--cflags` write that
 297|breaks the compile), but the specific flag pair does not belong to this file.
 298|
 299|`os_LoadBuildingEntityState` (`0x100128f0`) compiles in the real build with
 300|`/O2 /Gd /Oa /Ow /REBREW_TOOLCHAIN:msvc-6.0-sp5-pp`, set by `CMakeLists.txt` — it is one of the
 301|three sp5-pp-pinned files. Its metadata carried **no `cflags` field**, and the docs record
 302|`CMakeLists.txt` as the place where per-file flags live for exactly these files.
 303|
 304|Persisting the same flags into the metadata with `rebrew test --cflags "/O2 /Gd /Oa /Ow"` — the
 305|tool writes the field itself — makes `scripts/gate.sh` go **FAIL** with
 306|**`fatal error C1001: INTERNAL COMPILER ERROR`** and a C1083. The identical flags appended to the
 307|identical defaults work through the CMake path, so `/Oa /Ow` is not the problem: **the metadata
 308|path and the CMake path do not construct the same command line, and only the CMake one compiles
 309|this file.**
 310|
 311|**Check `grep '<file>.c.obj:' -A40 build/CMakeFiles/server_dll.dir/build.make` before adding any
 312|`cflags`**, and do not add a field that merely restates a CMake pin. Note also that
 313|`rebrew-functions.toml` is mode 444 — reverting needs `chmod u+w` first.
 314|
 315|## 6f. A dropped per-file flag produces a normal-looking measurement (rounds 879-880)
 316|
 317|`set_source_files_properties(... COMPILE_OPTIONS "/A" "/B")` **silently drops `/B`** — CMake wants a
 318|`;`-separated list. Configure succeeds, the build succeeds, `build.make` simply lacks the flag, and
 319|any measurement taken is of a *different compile than the one intended*, with no error anywhere.
 320|Round 45 nearly concluded "`/Oa` is inert" from exactly such a run.
 321|
 322|**Check the generated command line, not the CMake source, before believing a flag experiment:**
 323|`grep -A40 '<file>.c.obj:' build/CMakeFiles/server_dll.dir/build.make`.
 324|
 325|The plumbing was audited afterwards and is otherwise sound: all three `COMPILE_OPTIONS` pins and
 326|the zlib `COMPILE_FLAGS` reach their command lines, and of 57 files carrying metadata `cflags`, **0
 327|real flags are missing** — the 48 apparent misses are all `/DREBREW_ALLOW_NAKED`, which
 328|`C_DEFINES` supplies globally as `-DREBREW_ALLOW_NAKED=1`.

 330|## 7. The size rule has two branches, and mixing them discards good work
 331|
 332|`cl` pads each COMDAT to 16 bytes, so for an object with **no** relocated data after its code
 333|any real body at or below `16*ceil(size/16)` is composition-neutral, with **no lower bound**.
 334|If the object *does* carry a jump table or case map after its code, the **real** length binds
 335|and padding cannot protect it (`vfs_OpenStream`'s 8-byte shortfall was worth −36 linked). An
 336|earlier rule — "the real body must equal the reference's" — was strictly stronger than the
 337|composition requires and had been silently discarding admissible candidates.
 338|
 339|## 8. probe-span vs test-real: two rulers, one truth
 340|
 341|`probe_function` reports the padded COMDAT span as obj size (ExProdObjekt 1008, PCQ
 342|640); `rebrew test` reports the real body (993, 639). Their match
 343|counts differ accordingly (888 vs 976, 584 vs 624) — and test's
 344|match_count equals probe's matched-reloc bucket. Same object,
 345|different rulers. Always state which ruler a number comes from
 346|before comparing two figures.

 348|## 9. Build and verify side effects that burn
 349|
 350|- **A lone `C1083: Cannot open compiler intermediate file '<garbage>.tmp'` with no source location
 351|  is the build harness, not the source (round 894).** It appeared in a `gate.sh` run immediately
 352|  after a header change and read exactly like a compile-error regression introduced by that change.
 353|  It is a **transient parallel-build temp-file collision**: re-running the build produced **0**
 354|  errors and the gate then passed with all baselines held. The tell is the filename — `a00032gl`,
 355|  not a path, and not a `.c` file — and the absence of any line/column. Before treating a C1083 as
 356|  a finding, check whether any `error C####` line names a *source* file; if none does, rebuild
 357|  before touching the code. Setting `TMPDIR` or dropping to `-j4` avoids it.
 358|- **`cmake --build build` fails by design at the post-link layout step** with no
 359|  `error C####`/`LNK####`, and `make` then **deletes `build/server.dll`**. The deliverable must
 360|  be regenerated with `scripts/split_link.sh` + `postlink_residual.py --write`. Leaving the tree
 361|  after a bare build means the artifact is simply gone.
 362|- **`rebrew verify --full` rewrites `src/rebrew-functions.toml`** (it demotes `SIZE_MISMATCH` to
 363|  `STUB`) and the file is mode 444, so restoring it needs `chmod u+w` first.
 364|- **`scripts/linktest.sh` measures `.text` only, and a data-type change can be `.text`-neutral
 365|  while costing `.data`.** Round 521 replaced five overlapping array definitions in
 366|  `loadsave3.c` with correctly-typed scalars: `linktest.sh` reported `8634 -> 8634 (+0)`, and the
 367|  gate's `.data` ceiling caught **21,836 -> 22,072 (+236)** in the same change. `linktest.sh`
 368|  reads `.text`; only `gate.sh` reads the raw-link `.data`, and it is the only ruler that saw it.
 369|  Measure a data edit with `gate.sh`, not `linktest.sh`.
 370|- **The `.scratch/residue_base.log` that `linktest.sh` diffs against is not regenerated
 371|  automatically and can be many rounds stale.** A `+1` in that table is meaningless until the
 372|  baseline is refreshed; `bash scripts/linktest.sh --new-base <file.c>` rewrites it (and prints no
 373|  delta). Cross-check by reverting the edit and confirming the baseline reproduces.
 374|- **`cmake --build build -j8` on its own leaves the tree in a state that reports garbage residue.**
 375|  The post-link layout step fails by design and `make` then **deletes `build/server.dll`**, while
 376|  `build/split_poc/` keeps the object set from the previous run. Residue read from that state is
 377|  meaningless — round 889 measured **58,614** and then **116,814** from two such states, when the
 378|  true value was 8,634. Worse, it is *sticky*: `git checkout` of the sources restores `verify`
 379|  (281/283) but not the residue, so the tree looks reverted and still reports a false number. The
 380|  recovery is to delete the split state and take a full gate pass:
 381|  `rm -rf build/split_poc build/server.dll && bash scripts/gate.sh`.
 382|  **The tell is `split_link.sh` printing `exactly at their reference VA: 0`** — the same
 383|  composition-collapse signal `linktest.sh` refuses to measure through
 384|  (`msvc6-c-shapes.md` §124). Treat any residue number taken without a fresh `postlink_residual.py`
 385|  run after a source change as unmeasured, not as a regression.
 386|- **A `cmake --build` also deletes the deliverable**, so a round that builds to test something and
 387|  then compares residue is comparing a missing or stale artifact. Always rebuild the split state
 388|  before reading residue; never carry a number across a bare build.
 389|- **`rebrew verify --data` prints a `UserWarning` per `DATA` marker whose VA has no `name` in
 390|  `src/rebrew-data.toml`, and the marker is then dropped from the inventory as `unknown`.** The
 391|  warning text — "has no declaration on the following line and no name in the data metadata" —
 392|  reads like a *source* defect, but the marker can sit over a perfectly good definition; the
 393|  missing field is the metadata. Round 882: `vfs4.c` `0x1002944c` (`s_rb_1002944c` and four
 394|  siblings) and `vfs_OpenStream.c` `0x100294a4` (`s_0x_08X_length_100294a4`) both warned while
 395|  the definitions were present and relocating correctly. A previous `lint --fix` had written
 396|  **`section` only** into those two entries (TODO round 559, W016), and `scan_globals` needs
 397|  `name`, not `section`, to attribute the marker. Writing `name`/`type`/`size` through
 398|  `rebrew.data_metadata.set_data_field` (the same API `--fix` uses; run it from
 399|  `~/.local/share/uv/tools/rebrew/bin/python`, the repo venv lacks `zstandard`) cleared both
 400|  warnings and raised `verify --data` matched **83 -> 85**. A warning count here is not a
 401|  `.text` or `.data` measure: the gate held 8,634 / 21,836 unchanged across the edit.
 402|- **`rebrew verify --data` warnings go to stderr and are invisible to `--json` consumers that
 403|  pipe stdout only.** `2>/dev/null` drops them; the `matched` count is the only surviving signal,
 404|  and a silent drop lowers it rather than printing anything. Grep stderr when the count moves.
 405|- **`verify --data` compares only symbols that carry a name *and* a resolvable size, and it drops
 406|  the rest without saying so.** `data_verify.section_symbol_bytes` skips an entry with no `name`;
 407|  with no `size` it falls back to `estimate_type_size(type)`, and skips again if that fails. So
 408|  `matched` is a count of *attributable* symbols, not of `.data` symbols, and the number is not
 409|  comparable between rounds where naming changed. Round 883: 20 `.data` entries had `section`
 410|  only, were skipped unconditionally, and all 20 turned out to be byte-identical — `matched` went
 411|  **85 → 105** with no output change whatsoever. Read `matched` as coverage, never as correctness;
 412|  a `mismatched`/`missing` list is the only verdict here.
 413|- **`rebrew todo`'s `start-data` lane and `verify --data` are not the same set, and the lane can
 414|  never empty for link-produced data.** `start-data` is every metadata entry with a blank or
 415|  `UNCHECKED` status (`todo.py` `_collect_start_data`). The 18 `__imp__*` IAT slots qualify and
 416|  always will: they are linker output, not source definitions, so no source symbol can "verify"
 417|  them. Their bytes were confirmed identical to the reference at `0x10024000..0x10024044` in round
 418|  883. Treat a `start-data` item whose VA is in `.idata` as permanently unactionable rather than
 419|  as pending work.
 420|- **Most of this binary's "`.data`" is really BSS, so a `matched` tick on those symbols proves
 421|  nothing.** `.data` carries `rawsize 0xe000` over a `vsize 0x174059c`, so only
 422|  `0x10027000..0x10035000` has file bytes; every `.data` symbol above that is zero-fill.
 423|  `rebrew verify --data` compares via `pefile`-style section reads, and on a zero-fill VA it
 424|  compares zero against zero — a guaranteed match. Round 884 sized 57 `.data` symbols and
 425|  `matched` rose 105 → 108, but **54 of the 57 are above `0x10035000`**: the rise is accounting,
 426|  not verification. Before treating a data `matched` increase as evidence, check the symbol's VA
 427|  against the section's raw extent. `.bss` and `.idata` entries are in the same category.
 428|- **The built binary's `.text` / `.rdata` / `.reloc` VirtualSize already equal the reference's**
 429|  (`0x22846` / `0x2e81` / `0x10374`). A size-mismatch hunt on this target is a dead end; the
 430|  deliverable's remaining gap is *content* — 8,634 residue bytes inside `.text` — so measure with
 431|  residue, not with section sizes.

 435|## 10. How to check any claim in this document
 436|
 437|- Residue and per-function numbers: `bash scripts/linktest.sh <one source>` against
 438|  `.scratch/residue_base.log`, or regenerate with `scripts/split_link.sh` +
 439|  `scripts/postlink_residual.py --write build/server.dll`.
 440|- Frames, slot maps, prologues: disassemble `original/Server/server.dll` at the VA and compare
 441|  with the built image (`instr_diff.py <va> --built build/server.dll`).
 442|- Gap curves: `scripts/gaptrace.py <va> <source> _<symbol>` — **no size argument**.
 443|- Slot maps: the sentinel-initial probe (`msvc6-allocator.md` Finding 60).
 444|- Gate: `bash scripts/gate.sh` (lint + compile errors only + `verify --full` against a 281
 445|  baseline). Expect the build's post-link step to fail; only `error C####`/`LNK####` count.
