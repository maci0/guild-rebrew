 121|## 6. Three audit shapes that generate only false positives
 122|
 123|- **A hand-rolled struct-size calculator reports garbage on this tree — use the compiler instead
 124|  (round 895).** Two successive versions of a Python `sizeof` estimator flagged **18 then 7**
 125|  structs whose `// SIZE` comment disagreed with their declared extent. **All 25 were the
 126|  instrument.** Three separate failure modes, each invisible in the output:
 127|  - the first version double-counted array members (`PlayerList9 { int count; int ids[8]; }`
 128|    computes 0x24; it said 0x80 = exactly 2x);
 129|  - the second could not resolve a member whose *type is another struct*
 130|    (`SbhRegion.grpHeadList[32]` of `SbhGroup` at 0x204: 0x144 + 32*0x204 = 0x41c4, which the
 131|    header states correctly; the estimator assumed 4 bytes per element);
 132|  - one-line bodies (`typedef struct { int count; int ids[8]; } PlayerList9;`) parsed as a single
 133|    token pair.
 134|  **The compiler cannot be fooled and costs one invocation per type.** Write
 135|  `char chk[sizeof(T)==0xNN?1:-1];`, include the defining TU, and compile with
 136|  `rebrew-cmake-cl`. Doing that for the flagged types returned **48 of 48 correct**, including
 137|  `SbhRegion` 0x41c4, `SbhGroup` 0x204, `TGT` 0x3c and `gz_stream` 0x64. A regex over C is a
 138|  hypothesis about C; `sizeof` is a fact about it.
 139|- **A `C1083: cannot open include file` inside a size probe looks exactly like a size failure.**
 140|  `gz_stream`'s check failed until `-I references/zlib` was added — the assertion never compiled,
 141|  so "NOT 0x64" meant "did not build". Always separate *compile status* from *assertion result*
 142|  before reporting a type as wrong.
 143|- Naive same-mnemonic immediate comparison across a diff finds aligner
 144|  crossover (both sides contain both values in different interleave:
 145|  `cmp cl,2/6`, `shl 4/8`, push-constant runs). Without control-flow
 146|  awareness it cannot distinguish a constant bug from a phase shift.
 147|- Polarity-pair text comparison is void: `rebrew diff` prints branch
 148|  targets as relative displacements, so equal strings are coincidence.
 149|- Cross-image VA comparison is valid only for identical layouts. Byte-
 150|  decoding branch targets on both sides and comparing numerically
 151|  "found" three same-target polarity pairs; ground truth showed each
 152|  side's VA holds different code. Never compare addresses across two
 153|  differently-laid-out binaries.
 154|- **Raw-byte diffing against `.scratch/server.dll.prelayout` invents mismatches in every
 155|  relocated function (round 860).** That file is the *pre-postlink* link output, so its
 156|  absolute `mov`/`call` operands hold the linker's own values, not the reference's. Comparing
 157|  bytes directly made **241 of the 264 `RELOC`/`EXACT` entries look stale**, and tuning the
 158|  "is this a relocation?" heuristic only moved the count around (241 → 158 → 121 unexplained) —
 159|  the clearest sign the *instrument* was wrong rather than the data. Checked with the tool:
 160|  `rebrew verify` reports **0 entries with a nonzero delta**, and `rebrew test` on one of the
 161|  "suspects" returns `match_count 179/179, mismatches []` with `reloc_count 12`. The metadata
 162|  is consistent; the raw diff was not.
 163|- **A field-offset histogram cannot type a struct, and merging two histograms invents a layout.**
 164|  Round 893 collected every `slot + 0xNN` offset in the tree (98 distinct, `0x170` alone in 12
 165|  files) and merged it with the field map written in `spiel62.c`'s header. The merge *collided* —
 166|  `parent_index` (2 bytes at `0x27`) ran into `season_born` at `0x28` — and the tempting reading
 167|  was "one of the two sources is wrong." **Neither is: they describe different records.**
 168|  Disassembly settles it, and a histogram cannot. At `0x1000fe86`:
 169|  ```
 170|  0x1000fe76  call gm_StartFilteredEntitySearch   ; result in eax
 171|  0x1000fe86  mov  cx, word ptr [eax + 0x27]      ; a SLOT INDEX, 2 bytes
 172|  0x1000fe8a  cmp  cx, 0xffff
 173|  0x1000fea0  lea  ecx, [ecx*4 + 0x100358a0]      ; scaled by 540 -> g_slot_table
 174|  ```
 175|  So the record `gm_StartFilteredEntitySearch` returns carries a slot index at `+0x27` and is
 176|  **not** a `g_slot_table` element. The `g_slot_table` element separately has a 4-byte field at
 177|  `+0x28` (`0x1000fc9c  mov [eax+0x28], ecx` after `dec ecx`, the season store). A word at `0x27`
 178|  and a dword at `0x28` cannot coexist in one struct, so two types are in play.
 179|  **Rules this yields:** (1) `offsetof`-style sweeps tell you which offsets are *used*, never
 180|  which struct they belong to — same-base offsets from different functions may not share a base;
 181|  (2) when two field maps collide, disassemble the *producer* of the pointer (here, the call that
 182|  fills `eax`) before deciding which map is wrong; (3) a half-remembered regex is not a negative
 183|  result — `mov [r+0x28],r32` appeared absent because the pattern only matched the `disp8`
 184|  encoding, and the store exists.
 185|- **A type defined in a header is not a type in use.** `EntityStruct` (`game/entity.h`) is declared
 186|  with `// SIZE 0x21c` and referenced **three times tree-wide — its own definition and two
 187|  comments**. `entity.h` is included by 9+ TUs, but only for its `extern` globals. Do not count a
 188|  header type as "the layout is defined"; grep for *instantiations and member accesses*, which is
 189|  zero here. The same check applied to `PlayerSlot` gives 13 references and is real.
 190|  **Use the tool's own masked comparison.** `rebrew test`/`verify` already implement "equal
 191|  after masking relocations" — do not re-derive it by hand from a prelayout copy. If a raw
 192|  comparison against `build/server.dll` is wanted instead, that file is the *post*-postlink
 193|  output and its bytes are comparable; the prelayout copy is not.
 194|  **The whole-`.text` total is also wrong from the prelayout copy: it reads 50,296 against the
 195|  shipped file's 8,634** (round 863), because every unresolved relocation counts. So the
 196|  prelayout copy is not an oracle for a per-function residue *or* for the tree total — only
 197|  `build/server.dll` (and `rebrew verify`) are.
 198|  This is the second round this session (with 852) where a raw byte reading produced a
 199|  confident false finding that the tool's own number refuted.

 201|## 6b. `function_structure.json` sizes are 16-byte-padded; the toml's are real (round 866)
 202|
 203|Comparing a function's recorded size across the two inventories looks like it finds defects and
 204|does not. Across all 351 tracked entries, **163 disagree, always with the discovered size larger,
 205|and 160 of those discovered sizes are an exact multiple of 16** while 157 of the toml sizes are
 206|not. The discoverer rounds each extent up to a 16-byte boundary; `rebrew-functions.toml` records
 207|the real function length.
 208|
 209|Consequence: any by-size arithmetic over the discovered inventory silently over-runs into the
 210|next function, which is what produced round 861's "54 unattributed residue bytes" and round 27's
 211|"196-function gap" reading. Use the toml size for a function's real extent, and the discovered
 212|inventory only for *finding* functions the toml does not list.
 213|
 214|This is why `rebrew test --symbol <name>` can report a size the metadata never had:
 215|`gm_CalculateProductionValue` came back as `ref 81` there while both inventories and
 216|`rebrew verify` say 396/400. When a size looks wrong, check it against **the next tracked VA**
 217|(`0x10019720 + 400 == 0x100198b0`) — that is the ground truth, not either inventory.

 219|## 6c. Object size can move toward the target while the link moves away (round 868)
 220|
 221|`gm_FindNextFilteredEntity` (`0x10016f80`) is 4 bytes short of the reference: object **342**
 222|against target **346**, and the deficit is a *missing block* — 8 instructions the reference has
 223|and we do not (`jne` + a full epilogue: `xor eax,eax` / store / four pops / `ret`). The reference
 224|reaches **one shared epilogue via a `cl`-flag jump**; we emit a private return at each early exit.
 225|
 226|Routing the offending early `return 0;` through the shared tail (`match = 0; goto done;`) moves the
 227|object **342 -> 347** — past the target by one, i.e. the size gap closes. At the link it is
 228|**+114 worse** (`gm_FindNextFilteredEntity` 215 -> 329, `.text` 8,634 -> 8,748).
 229|
 230|So "the object size now matches" is not evidence of progress, and on this function it is
 231|positively misleading: the same edit that fixes the size adds 114 residue bytes, because the new
 232|`goto` re-lays the block graph and the shared tail stops being reachable the way the reference
 233|reaches it. **Measure at the link or do not claim a direction** — this is the concrete case behind
 234|the AGENTS.md warning that the two object rulers disagree with each other and with the link.
