 220|are used directly with proper `#include` headers — no `extern` declarations
 221|needed.
 222|
 223|The compiler intrinsic `__ftol` (float-to-long) is statically linked and
 224|requires a forward declaration where used.
 225|
 226|Small static helpers within a module may omit the prefix (they were `static`
 227|in the original source and not visible across translation units).

 229|## Function Naming
 230|
 231|### Pattern: `prefix_VerbNoun`
 232|
 233|```
 234|cm_ExSellObjekt        -- cm  = command module
 235|                       -- Ex  = execute (action verb)
 236|                       -- Sell = English verb
 237|                       -- Objekt = German noun (object)
 238|
 239|cm_ChkMoveCredits      -- Chk = check / validate
 240|gm_AllocBuildingDefaults
 241|lb_ExPlayerlist
 242|ahm_ExAllocAlchemist
 243|gv_ExAllocGraveyardWorker
 244|sim_CreateCitizen
 245|```
 246|
 247|### Command Module Sub-Prefixes
 248|
 249|The `cm_` module uses a two-phase check-then-execute architecture.
 250|Each command type has up to two handler functions:
 251|
 252|| Sub-prefix    | Role        | Return semantics                     |
 253||---------------|-------------|--------------------------------------|
 254|| `cm_Chk*`     | Validate    | `0` = OK, `1` = invalid (reject)    |
 255|| `cm_Ex*`      | Execute     | `0` = OK, `1` = failed              |
 256|
 257|Both share the signature `int __cdecl func(void* cmd, void* result)`.
 258|
 259|Additional patterns seen in the binary:
 260|
 261|| Pattern           | Role                                          |
 262||-------------------|-----------------------------------------------|
 263|| `cm_Request*`     | Client-side command request (TL.exe only)     |
 264|| `cm_Dispatch*`    | Routes to a sub-handler                       |
 265|| `cm_Chain*`       | Linked command chain handler                  |
 266|| `cm_Init*`        | Initialization / default setup                |
 267|| `cm_Assign*`      | Assigns IDs or counters                       |
 268|| `cm_Get*`         | Read-only query                               |
 269|| `cm_Set*`         | Write a flag or field                         |
 270|| `Cmd*`            | Likely the compiled name for some cm_Ex       |

 318|## Variable Naming
 319|
 320|### Globals
 321|
 322|Globals use a `g_` prefix. When the original name is unknown, the convention
 323|in this project is `g_<hex_address>`:
 324|
 325|```c
 326|extern int g_next_object_id;              /* known purpose, partial name */
 327|extern char g_player_slot_0[];            /* known: player slot array */
 328|extern char g_slot_table[];/* known: static entity table */
 329|extern int g_entity_type_table;           /* known: entity type lookup */
 330|extern int g_1009b764;                    /* unknown: address-only name */
 331|```
 332|
 333|### String Constants
 334|
 335|Ghidra labels string constants as `s_<truncated_content>_<address>`:
 336|
 337|```c
 338|extern char s_cm_ChkMoveCredits____Invalid__qu_1002c7a4[];
 339|extern char s_D__Develop_DieGildeAddOn_command_1002c748[];
 340|```
 341|
 342|The embedded content reveals original function names:
 343|`s_cm_ChkMoveCredits____...` means the string literal starts with
 344|`"cm_ChkMoveCredits(): ..."`.
 345|
 346|### Locals
 347|
 348|Original local variable names are lost. Ghidra assigns type-prefixed
 349|temporaries (`iVar1`, `puVar2`, `pcVar3`). During decompilation we replace
 350|these with descriptive names based on context:
 351|
 352|```c
 353|/* Ghidra output */
 354|int iVar1;
 355|ushort *puVar2;
 356|
 357|/* Reversed */
 358|int resolve_result;
 359|unsigned short *building_entity;
 360|```

 362|## Calling Convention
 363|
 364|| Code origin | Convention   | Default for             |
 365||-------------|-------------|-------------------------|
 366|| GAME        | `__cdecl`    | All cm_, gm_ functions  |
 367|| Win32 API   | `__stdcall`  | `__declspec(dllimport)` |
 368|| CRT         | `__cdecl`    | Standard library        |
 369|
 370|Symbol mangling: `__cdecl` functions get a leading underscore in the object
 371|file. Annotation `// SYMBOL: _cm_ExFree` reflects this.
 372|
 373|## Error Logging Convention
 374|
 375|Every important function logs errors through a central logger:
 376|
 377|```c
 378|LogMessageInternal(
 379|    s_D__Develop_DieGildeAddOn_command_1002c748,  /* __FILE__ */
 380|    0x2a21,                                        /* __LINE__ (hex) */
 381|    s_cm_ExFree____Can_t_free_Objects_1002cc3c,   /* message */
 382|    1                                              /* severity */
 383|);
 384|```
 385|
 386|The message string almost always starts with the function name:
 387|`"cm_ExFree(): Can't free Objects"`. This is how we recover original names.

 389|## Attested Names from Embedded Strings
 390|
 391|The shipped binaries embed the full string corpus. RevEng.AI's
 392|`GET /v2/analyses/{id}/functions/strings` returns every string with the
 393|function VA that references it. A string shaped `"<name>(): ..."` or
 394|`"<name>: ..."` names the owning function.
 395|
 396|Every name below was then **verified against the code**: the function at the
 397|stated VA is disassembled and confirmed to push the literal address of that
 398|string. RevEng's attribution alone is not trusted (it wrongly attached
 399|`_main_:` to `0x100068e0` and `lb_ExPlayerReadyStatus` to `0x100146c0`).
 400|
 401|Reproduce:
 402|
 403|```bash
 404|# list every string a function references; "(): " prefixes name the owner
 405|curl -s -H "Authorization: Bearer $REVENG_API_KEY" \
 406|  "https://api.reveng.ai/v2/analyses/1468081/functions/strings?page_size=2000" \
 407|  | jq -r '.data.strings[] | select(.value|test("^[A-Za-z_]+\\(\\):")) | "\(.functions[0].function_vaddr)\t\(.value)"'
 408|# then confirm the owner pushes the literal
 409|rebrew asm 0x<VA> --size <size> | grep 'push 0x100[23]'
 410|```

 453|### Module case: `m_alloc` is snake_case
 454|
 455|The `Units/m_alloc` unit does not use the `m_VerbNoun` CamelCase of the game
 456|modules. Its recovered names are lower snake case:
 457|
 458|- `m_alloc` — the tracked allocator, called from every unit. In the original
 459|  this is a macro: the tracked implementation receives an extra
 460|  `__FILE__ ":" __LINE__` argument, so our `m_AllocTracked` stays as the
 461|  implementation name and only the macro was `m_alloc`.
 462|- `m_init` — sets the slot count and allocates the slot table;
 463|  `m_alloc` refuses to run before it.
 464|- `m_pool_free` — pool release.
 465|- `m_alloc_debug` — not a function: a block group name written by `sprintf`,
 466|  so it must not be turned into a symbol.
