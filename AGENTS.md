## Quick Start

```
1. rebrew todo --json                          # get highest ROI action items
2. rebrew lib-match --stock-lib LIBCMT.LIB --va 0x<VA>   # is it already in a library?
3. rebrew skeleton 0x<VA>                      # generate .c skeleton
4. rebrew test src/Develop/<path>/<func>.c --json  # compile + compare
5. # iterate code until STATUS: EXACT or RELOC
6. rebrew test --all --json                    # batch promote all ready functions
```

> [!IMPORTANT]
> **Check step 2 before reversing anything.** Statically linked library code
> sits in `.text` looking exactly like game code, and reversing it is wasted
> work: the linker supplies those bytes anyway. All 68 functions that once
> lived under `crt_region/` were stock LIBCMT, reversed by mistake and matched
> for weeks before anyone checked.
>
> Use `rebrew lib-match`, not `rebrew flirt`, for this question. FLIRT
> matches short byte patterns against prebuilt signatures and identifies 9 of
> those 68 (25 library functions across the whole binary; regenerating the
> signatures from this exact LIBCMT raises it to 37, still 9 of the 68). The
> check above compares whole function bodies against the library actually
> being linked, ignoring relocation slots, which is why it finds all 68. It
> also runs as a pre-commit hook over the whole tree.
>
> The LIBCMT hook covers the default (server) target only. **The `Europa1400Gold_TL.exe`
> (GOLDTL) client statically links `d3dx8.lib` (DX8.1 SDK) too**: 907 functions
> (~273 KB) in `.text` band `0x5e0000–0x64ffff` are linker-supplied D3DX8 bodies,
> marked `// LIBRARY: D3DX8` in `src/library_d3dx8.h`. Before
> reversing any GOLDTL function in that band (or a `0x4b5xxx` `.text`-side D3DX8
> string site), check both:
>
> ```
> rebrew lib-match --lib references/dxsdk8/lib/d3dx8.lib --target Europa1400Gold_TL.exe --va 0x<VA>
> # 907 VAs already LIBRARY-marked -> lib-match returns nothing for them
> ```
>
> `Europa1400Gold.exe` (GOLD) does NOT statically link DirectX; its DX is pure DLL
> import (`DDRAW`/`DINPUT`/`mss32`), so no D3DX lib-match applies there.

## Annotation Format

Every reversed `.c` file starts with a **stable identity header**: only the
information that is intrinsic to the function and never changes:

```c
// FUNCTION: SERVER 0x<virtual_address>
// SYMBOL: _function_name                 ← optional, derived from C definition

void __cdecl function_name(void)
{
    // stub
}
```

Volatile metadata (status, size, compiler flags, notes, blockers) is stored
**outside** the `.c` files, in `src/rebrew-functions.toml` (data globals in
`src/rebrew-data.toml`), keyed by `<marker>.<VA>`:

```toml
["SERVER.0x10001234"]
status = "STUB"
size   = 42
cflags = "/O2 /Gd"
blocker = "register allocation"
note   = "inline asm detected"
```

> [!CAUTION]
> **Never manually edit `src/rebrew-functions.toml`.** It is managed exclusively by Rebrew
> CLI tools (`rebrew test`, `rebrew match`, `rebrew diff --fix-blocker`, etc.).  Manual
> edits will be lost or corrupt the file and break tool workflows.

**STATUS values**, strongest claim first: `EXACT` (byte-perfect) > `RELOC` (match after
masking relocations) > `NEAR_MATCHING` (close) > `STUB` (incomplete). `PROVEN`
(semantically verified) is **not** a byte match and does **not** outrank `EXACT`: it ranks
**below** `RELOC`, because a proven function still compiles to bytes that differ from the
target (every PROVEN entry carries a non-zero delta). PROVEN is sticky against automatic
demotion, but `EXACT`/`RELOC` always override it, and it must never be counted, reported or
labelled as byte-matched. `SIZE_MISMATCH`
and `MISSING_SIZE` are stored when the object size disagrees with the binary.
`NEAR_MATCHING` appears only in `rebrew verify` output, never in the metadata.

`CFLAGS` is optional and falls back to the target default from `rebrew-project.toml`.

## Compiler Constraints (msvc6)

- **C89 only**: no `for(int i=...)`, declare all variables at block top
- **Comments in code**: use `/* */` only (C89). `//` is used exclusively for annotation headers
- **Symbol decoration**: `_func` for `__cdecl`, `_func@N` for `__stdcall`
- **No `/GS`** (buffer security), no `__declspec(noinline)`
- **Execution**: all CL.EXE/LINK.EXE calls run through the docker image
  (`rebrew/msvc:6.0-sp6-win32`); build it with `rebrew toolchain build msvc-6.0-sp6`
  before `cmake --build`
- **CFLAGS are per-file in practice**, not per-function: a flag one function
  needs can break a file-mate. See `docs/msvc6-c-shapes.md` section 12.

## Linking

Build with `cmake -S . -B build -DREBREW_DEBUG_INFO=OFF && cmake --build build`.

**Run `scripts/gate.sh` before committing.** It is the checks that must pass:
`rebrew lint`, the compile (the POST_BUILD postlink step is expected to fail
until the tree is position-aligned, so only `error C####`/`error LNK####`
count), `rebrew verify --full` against a baseline of 265 passed (EXACT+RELOC), the linked
`.text` residue against `RESIDUE_BASELINE`, and the per-target toolchain
alignment check (`rebrew toolchain detect`: code-generator family vs
configured profile). A drop below either
baseline is a regression; lower `RESIDUE_BASELINE`, or raise `BASELINE`, only
when a change improves the number.

**Judge every candidate with `scripts/linktest.sh <file.c>`, not with object
scores.** It recompiles the file with the exact command `build.make` records,
relinks, applies postlink, and prints a per-function residue delta against
`.scratch/residue_base.log`:

```
$ bash scripts/linktest.sh src/Develop/DieGildeAddOn/game/spiel_c/gm_AllocSpieler.c
function                                  before   after   delta
gm_AllocSpieler                             2824    2866     +42  <-- worse
.text total 8652 -> 8694  (+42)
revert candidates: gm_AllocSpieler (+42)
```

This matters because the object rulers routinely disagree with the link and
with each other. `rebrew test`'s `match_count` is a *positional* compare, so a
size change anywhere moves every byte after it; `probe_function.py`'s `aligned`
is structural. A measured case: hoisting one store in `gm_AllocSpieler`
reproduced the reference's instruction sequence exactly and moved `aligned`
662 → 665 while `match_count` fell 1004 → 947 with `obj_size` unchanged, and
at the link it was **42 bytes worse**. When the two object rulers disagree,
link and find out; do not reason about which one deserves trust
(`docs/msvc6-c-shapes.md` sections 19, 116, 118).

- **`REBREW_DEBUG_INFO` must be OFF.** With it ON, `/debug` adds a 0x1c-byte
  debug directory that grows `.rdata` past the reference, and the postlink
  layout step fails with "built .rdata prefix size does not match".
- **Link stock libraries. Never patch a `.lib`.** When a library object drags
  in something the reference does not have, displace it with a local
  definition of the symbols it provides (see the `_CRT_REGION_KEEP` comment in
  `CMakeLists.txt`) or change what references it. The build once linked a
  hand-stripped LIBCMT kept in gitignored `.scratch/`, which no fresh clone
  could reproduce; `rebrew lib-match --stock-lib` refuses to run if the
  extracted copy differs from the toolchain image's.
- **A duplicate-symbol warning is a finding, not noise.** `LNK4006` usually
  means either the same global is defined in several translation units, or
  something the library already provides has been reimplemented. Resolve it
  rather than silencing it with `/FORCE:MULTIPLE`. **Measured on a full
  `--clean-first` rebuild (round 910): six `LNK4006` occurrences over three
  symbols, all library displacement rather than game-TU duplication**:
  `_putc` (`LIBCMT.lib(fputc.obj)` against `link_stubs.c.obj`), `__amsg_exit`
  and `___app_type` (both `LIBCMT.lib(dllcrt0.obj)` against `amsg_exit.c.obj`
  and `link_stubs.c.obj`): `dllmain.c` calls `_CRT_INIT`, which pulls
  `dllcrt0.obj`. Earlier notes here said "two cases"; the real count is three
  symbols, and note that an *incremental* build prints none of them, so the
  count is only visible after `--clean-first`. When triaging a new warning,
  check whether the losing definition is a `LIBCMT.lib(...)` object; that is
  the displacement pattern; a warning between two game `.obj`s is the
  duplication pattern the rule is about.
- **Compare the import table against the reference** after any link change.
  An extra import means a library object came in that the original did not
  have; a missing one means the opposite. The reference has exactly 100.
- **Compare the built `.text` VirtualSize against the reference** after any
  link change: 0x22846. `rebrew postlink` patches by `.text`-relative offset
  and now refuses a `.text` that is not position-aligned (it validates the
  layout package's sparse maps and fails below 90% coverage), but the number
  itself is the cheap check. A built `.text` *shorter* than the reference means
  code the reference contains is not being emitted: `cce0a1b` linked 0x2344f
  (trimmable, correct) and `93ecf29`, converting the naked `_emit` dumps to
  proper C, linked 0x1edc2, 0x3a84 short, which is the state the tree is in
  today. See `docs/TODO.md`, "`.text` link shortfall".

**Look the address up first; do not grep the docs by keyword.** The entries
are keyed by address, and a `grep` only works if you already know the words the
entry used. Round 853 spent a whole round re-deriving `msvc6-c-shapes.md`
section 127, whose exact instruction pair and decisive probe were already
recorded, because the shapes doc was searched last rather than first:

```
python3 scripts/whathas.py 0x10009838              # what is recorded at this VA
python3 scripts/whathas.py 0x10009838 --window 64  # widen the band
python3 scripts/whathas.py --va 0x10018850 0x10019730   # a function's whole span
```

alike, and cites section + line. `docs/README.md` maps which doc answers what. Run it
on the anchor address *and* on the enclosing function's span before probing
either. "No documented probe" is not proof of novelty (still check the file
header), but a hit means the round is already written.
