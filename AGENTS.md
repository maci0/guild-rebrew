## Source Addresses and Metadata

C source may carry an optional address immediately above a definition or variable:

```c
/* ADDRESS: Europa1400Gold_TL.exe 0x10001234 */
void __cdecl function_name(void)
{
    /* stub */
}
```

Stack one address per target above a shared declaration. Comments and blank lines
may intervene; code and directives may not. New generators include these anchors.
All state and identity live in format-2 metadata: `rebrew-functions.toml`,
`rebrew-data.toml`, and `rebrew-source.toml`. The identity field is `kind`.
`source = "naked"`, STRUCT/CALLERS information and support file purposes are
metadata-only. Old inline blocks and earlier metadata formats are rejected;
there is no compatibility parser or marker migration command.

Use `rebrew source register --dry-run` to preview declaration-bound identities,
then register them without `--dry-run`. Registration preserves existing state.
For a support file, use `rebrew source register FILE --support "reason"`.
Metadata-only bindings remain valid without address comments. Never hand-edit
stores or STATUS; use the locked metadata owner APIs and comparison commands.

**STATUS values**, strongest claim first: `EXACT` (byte-perfect in the object, or
in the raw link: linked EXACT) > `RELOC` (match after masking relocations) >
`NEAR_MATCHING` (close) > `STUB` (incomplete).  `PROVEN`
(semantically verified) is **not** a byte match and does **not** outrank `EXACT`: it ranks
**below** `RELOC`. Its proof depends on the modeled inputs, calls, and loop
bounds; it does not establish identical bytes.  PROVEN is not sticky: the next
`rebrew test`/`rebrew verify` records the byte result over it, and it must never be counted,
reported or labelled as byte-matched.

A **linked EXACT** is EXACT earned in the raw link: the function is RELOC in the
object compare, but the raw linked image places it at its reference VA and its
bytes there equal the reference with no masking, so the linked bytes are
identical. `rebrew verify --text --raw-link` records it (the raw link only, never a
postlinked image; configured `raw_link` counts as the acknowledgement) with the
image path and SHA-256 in `verification`. Run it after any link that is
byte-identical to the reference. It stays EXACT while the compile inputs and the
image hash are unchanged; a rebuilt image with different bytes or an input
change returns it to RELOC until the next `rebrew verify --text --raw-link`, and any
real byte difference demotes it as usual.

`rebrew source rename` carries reviewed assembly provenance with definitions and
file moves, refreshing only records current before the rename. Stale evidence
stays stale. Reverify byte matches after renaming.

`origins` records accepted external fields; `verification` records comparison
inputs and measurement time independently of ordinary `updated_by` /
`updated_at` edits. Re-run verification after source/header/compiler changes.
These facts survive removal of derived coverage and compile caches.

`CFLAGS` is optional — falls back to the target default from `rebrew-project.toml`.

Types have stable IDs rather than instance VAs. Put definitions in the owning
subsystem header or private C file and bind them with `rebrew types bind`.
Keep C size separate from evidenced native allocation/stride extent; unknown
semantic fields can remain byte regions. `rebrew-types.toml` is CLI/API-managed

change, review the native evidence and rebind the same ID. Heap instances are

## Compiler Constraints (msvc-6.0-sp5-pp)

- **C89 only**: no `for(int i=...)`, declare all variables at block top
- **Comments in code**: use `/* */` (C89). Do not add a `// FUNCTION:` line; identity is a `MODULE.0xVA` row
- **Symbol decoration**: `_func` for `__cdecl`, `_func@N` for `__stdcall`
- **No `/GS`** (buffer security), no `__declspec(noinline)`
- **Execution**: all CL.EXE/LINK.EXE calls run inside the toolchain's docker image (wine lives in the image; there is no host wine/wibo fallback)

## Linking

Library origin and build provider are separate facts. `LIBRARY` marks
library-derived code. It does not choose the provider.

- Built from source: the body is a project `.c`, including vendored or adapted
  libraries and sources outside `reversed_dir`. Verify compiles it. Bind a
  header identification with
  `rebrew library bind-source <va> <source> --symbol <native-symbol>`.
- Statically linked: a unique native symbol in a configured external archive
  appears in the raw link map. Leave that member linked. Check it with
  library matching and the raw linked image.
- Unresolved: neither fact is present. Do not infer a provider from the name.

When both a source and a map entry exist, the source wins. Keep compiled
library results separate from game reversing progress.

Bind placeholder calls to an existing function or header-owned `LIBRARY` identity
with `rebrew source rename PLACEHOLDER MODULE.0xVA --dry-run`, then apply after
reviewing the preview. Name binding preserves the destination identity/verdict;
establish its build provider separately through source, archive and raw-map evidence.

- **Link stock libraries. Never patch a `.lib`.** When a library object drags
  in something the reference does not have (an extra import, duplicate data),
  displace it with a local definition of the symbols it provides, or change
  what references it. A hand-edited library cannot be reproduced from a clean
  checkout, and it hides the duplication that library-detection depends on.
- **A duplicate-symbol warning is a finding, not noise.** `LNK4006` /
  `LNK4217` usually means either the same global is defined in several
  translation units, or you have reimplemented something the library already
  provides. Resolve it rather than silencing it with `/FORCE:MULTIPLE`; keep
  the flag only for cases you have identified and written down.
- **Compare the import table against the reference** after any link change.
  An extra import means a library object came in that the original did not
  have; a missing one means the opposite.

## Global ownership

- **One storage owner per global.** The owner is the source definition or linked
  library object that allocates its bytes. `extern` declarations, headers, DATA/GLOBAL
  rows, and referring functions are declarations or users, not additional owners.
  Keep definition owners, declaration sites, and users separate in inventories;
  an extern-only scan cannot establish a library owner. `rebrew data list` uses the
  raw link's MSVC map (`--link-map` overrides it) to identify archive members;
  COMMON attribution also requires a unique definition in a selected, configured
  archive member. Keep uncertain aliases unresolved.
- **Separate game and runtime globals by provenance.** Keep game declarations in
  game or subsystem headers and CRT declarations in one CRT header. Physical
  `.data`/`.rdata`/`.bss` placement does not establish logical ownership: game
  constants near CRT code still belong to the game. Headers contain `extern`
  declarations; game storage is defined once in its owning translation unit.
- **Linked stock libraries own their code and data.** When the CRT is fully linked,
  describe its globals with declarations and annotations; do not create replacement
  CRT `.c` definitions or copied data blobs. Any necessary local displacement must
  name the displaced library member and explain why the reference needs it.
- **An interior address is a view, not another allocation.** Record its backing
  object, offset, type, and complete extent. Byte-span inventory and layout padding
  are layout facts; they must not become duplicate globals or pretend CRT owners.
- **Record storage relationships explicitly.** Use `rebrew data set --storage-kind`
  for objects, aliases, compiler literals, layout spans and imports;
  `--backing` identifies a view's allocation, and `--link-symbol` records
  a verified native symbol. Import slots are linker-owned pointers. Spans have
  no standalone owner. Coverage and dashboard declarations are never owners.
- **Reuse the canonical declaration.** Prefer the owning subsystem header over
  repeated per-function externs. Preserve proven compiler-sensitive declaration
  order when consolidating; verify affected functions after header changes.
- **Resolve gaps from evidence.** Establish VA, full extent, section, and provenance
  before creating storage. Check the binary's sections and zero-filled virtual
  tail; use the CLI or locked metadata APIs for metadata changes. Preview header
  generation, ownership moves, and padding emission, and reconcile generated or
  imported headers with existing game/CRT boundaries before replacing them.

## Naming

Every name follows the original developers' schema in `docs/naming_conventions.md`:
functions, globals, locals, types, constants and file names.

- An attested name wins: a `fn(): ...` log string or `__FILE__` path in the server or
  either client. Keep its original spelling (`gm_ObjectsAvailble`, `Objekt`).
- Otherwise use the module prefix and `VerbNoun` (`cm_`, `gm_`, `ahm_`, `gv_`, `sim_`,
  `amt_`, `ls_`, `plt_`, `m_`, `vfs_`, ...; `fio_` infix for file I/O). Never invent a
  prefix; units without an attested prefix keep unprefixed descriptive names.
- Globals follow the original style shown by the binaries' allocation labels and log
  strings, not a project `g_` prefix: attested names exactly (`lpGebaeudePROT`,
  `lpObjekteINST`, `gm_ObjektNr2MinimalHersteller`, `cm_LastSyncCount`); module globals
  `<module>_CamelCase`; heap table pointers `lp` + German noun (+ `PROT`/`INST`); file
  statics `s_`; typed pointers `tp_`; packet and struct fields German snake_case
  (`quell_besitzer_id`). Structs `UPPER_CASE`, constants `prefix_UPPER_SNAKE`.
- Compiler literals have no source identifier; their data rows use `str_<content>`
  (strings) and `flt_`/`dbl_<value>` (float pools), never `s_`.
- Layout spans and gap fillers are rebrew inventory, not original names; they keep
  their `g_before_*`/`g_gap_*` row names until an owner is proven.
- Record an unattested name as inferred where its row or doc entry lives.
